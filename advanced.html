Advanced concepts companion: LLM wikis, second brains, context engineering and software factories

Pairs with emerging concepts (the dated, evidence-labeled list) and with companions 2, 5. Public pages and primary posts only; no X account was used. The software-factory section was re-checked against its primary pages on 2026-10-04.

How to use this page

For each concept: what it is, how strong the evidence is, the best counterpoint, the question to ask, and a small reversible experiment. Evidence labels: evaluated, practitioner report, demo or claim, framework.

1. The compiled wiki

  • What it is: an LLM builds and maintains a linked set of notes between you and your raw sources (Karpathy's note: raw sources, wiki, schema; ingest, query, lint).
  • Evidence: framework plus practitioner description; Perplexity's post is a vendor report about its own product.
  • Counterpoint: the index approach is described at moderate scale; errors can compound without spot checks. No controlled comparison with retrieval was found.
  • Ask: who is accountable for accuracy, and how often is it linted?
  • Experiment: ten shareable sources, a read-only source folder, a one-page rule file, spot-check three pages.

2. Second brains: flat files versus scoped vaults

  • What it is: a "second brain" for an agent. The flat-file version is Markdown folders with one root index file. The scoped-vault version separates what the agent cannot see, can only read, and can change.
  • Evidence: both are practitioner material with no measurements seen. See the side-by-side comparison.
  • Counterpoint: an index is a map, not a maintenance process; scoped access adds setup and depends on one app.
  • Ask: should the agent see everything, and who checks accuracy?
  • Experiment: start with five files and an index; add access limits before adding anything private.

3. Context engineering

  • What it is: designing everything the model sees, not only the prompt wording. Chase's June 2025 definition: "building dynamic systems to provide the right information and tools in the right format". Anthropic frames it as curating the best set of tokens during a run.
  • Evidence: practitioner framework, widely adopted as a term, no single benchmark.
  • Counterpoint: can be a rebrand of prompt engineering; ask what changed in practice.
  • Ask: what is on the desk, who decided, and what happens when the answer is absent?
  • Experiment: write a one-paragraph standard brief for a recurring task and compare outputs with and without it.

4. Agent memory

  • What it is: persistent notes (files, wikis, graphs) so an agent improves across sessions. Research papers in 2026 explore graph-based and brain-inspired memory designs.
  • Evidence: academic benchmark results on their own setups; transfer to everyday use unproven.
  • Counterpoint: more memory can mean more stale or wrong memory; personal and agent notes need separation.
  • Ask: can you read, correct and delete what it remembers?
  • Experiment: find out how a product's memory works (a stored note you can edit, or just recent chat?).

5. The software factory and five levels of AI-assisted coding

  • What it is: Dan Shapiro's five levels of AI-assisted programming, from "spicy autocomplete" (0) through the coding intern, junior developer and developer to the engineering team (4) and the "dark software factory" (5). Level 5 is, in Shapiro's words, "a black box that turns specs into software", and he says he knows a handful of small teams (under five people) doing it. Shapiro's post (2026-01-23); Willison's summary (2026-01-28).
  • The reported example: Simon Willison saw a demo from a StrongDM team that follows this pattern. Nobody reviews AI-written code, the system's goal is to prove the software works, and humans design that system. In its public description the team states two rules, "Code must not be written by humans" and "Code must not be reviewed by humans", and says its method relies on written end-to-end "scenarios" kept outside the code agents can see, plus simulated copies of the third-party services the software depends on. Willison's account (2026-02-07).
  • Evidence: Level 5 is a demo and claim by the team, plus a practitioner report from Willison, who says the work "looked very convincing" and that some team members had 20+ years of experience on high-reliability systems. No independent evaluation was found.
  • Counterpoints:
  • Willison asks how anyone can prove software works when agents write both the code and the tests, and notes tests only help if agents do not cheat with something like assert true.
  • The Stanford CodeX analysis (Eran Kahana, 2026-02-08) is an opinion and legal-risk piece. It argues that agents optimize for passing tests, reports that the team's agents once wrote code that returned true to pass tests, and raises who is accountable when no human reviewed the code or wrote the tests. It also notes that the team's satisfaction measure is judged by AI.
  • Cost: the team's own rule of thumb is at least $1,000 on tokens per day per human engineer. Willison notes that at that level it becomes a business-model question, and hopes the patterns work at much lower spend. This is a company statement, not a measured cost.
  • Why it matters: it is a maturity model for one domain, a good worked example for the maturity episodes, and a warning against treating the top rung as the goal.
  • Ask: what does a wrong output cost in my work, and what proves correctness once I stop reading it?
  • Experiment: take one task you review by hand today and write down which automated check would convince you it was right, and who would be accountable if it was not.

6. Capability overhang

  • What it is: the claim that current models can do much more than people use them for (Mollick, September 2026).
  • Evidence: practitioner report from demonstrations by one author. Model names and capability claims in that post were not independently checked, and none are repeated here.
  • Counterpoint: demos are chosen by the person showing them. Ask how often it works on ordinary tasks.
  • Experiment: try one task you have not tried with current tools, and note the failure rate.

Reading rules

  1. Find the evidence label first. 2. Ask what the author sells or benefits from. 3. Find the counterpoint before trying the idea. 4. Run one small, reversible experiment.

Where these sit on the maturity ladder

Ad hoc use, then a repeatable brief, then a standard shared practice, then measured results, then continuous improvement. Every concept above is a way to climb one rung in one domain; none removes the need for review where a wrong output is costly.
